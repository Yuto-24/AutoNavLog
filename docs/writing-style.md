# 読者向け文章の規範

PR・Issue・コメント・ROADMAP・作業報告・最終回答に適用する。
日本語・英語のどちらでも、読者が現在地を把握し、判断や次の行動を選べる文章にする。
単に短くするのではなく、読者に情報の分類や時系列整理をさせない。

## 必須ルール

1. **結論を先に書く。** 冒頭に目的に応じた結論・現在地・読者への影響を書く。判断や操作が必要なら、何を決める／行う必要があるかを明示する。不要な依頼は作らない。
2. **1つのまとまりで1つの問いに答える。** 1段落・1箇条書きに実装、検証、公開、残作業、過去の経緯を詰め込まない。短文を基本とし、話題が変わったら段落を分ける。
3. **本文は現在地に編集し直す。** 更新のたびに経緯を追記して作業日誌にしない。古い説明・重複を整理し、必要な実績や判断の経緯は履歴・根拠リンクに残す。無関係なユーザー編集を消さない。
4. **事実・提案・未確認を区別する。** 実装済み、マージ済み、本番反映済み、受入済みを混同しない。テスト成功、未実施、失敗、実行不能も区別する。確認できない状態を断定しない。
5. **根拠は本文の判断を支える位置に置く。** まず何を確かめて何が分かったかを書く。SHA、CI実行番号、長いコマンド、詳細ログは補足・履歴・直接リンクに分ける。ただし、その識別子自体が判断対象なら本文に残す。リンクを検索URLに置き換えない。
6. **注意書きを重ねない。** 共通の制約はまとめて1回説明する。安全、データ損失、セキュリティ、公開可否など判断を左右する重大なリスク・未確認事項は冒頭にも明示し、簡潔さのために隠さない。
7. **具体的な名前を使う。** Issue・PRは「#番号 内容名」で参照する。抽象的な見出し、略語だけの説明、曖昧な「対応済み」を避ける。
8. **構成は目的に合わせる。** 下記の標準構成を使いつつ、短い返信に不要な見出しや空の節を作らない。全段落を同じ型に当てはめない。表は比較・工程の一覧に有効な場合だけ使う。

本規範は文章の編集方法を定めるものであり、操作権限や通知範囲を広げない。
既存の承認条件、機械が読む契約、API・schema・コード、引用原文、生ログを文体の都合で変更しない。
UI文言の決定にはAGENTS.mdの既存手順を適用する。
相違・不具合・未検証の重要事項を省く根拠にもしてはならない。

## 用途ごとの標準構成

### PR

- 目的：解決する問題と変更後の効果。
- 変更内容：意味のある変更を短い箇条書きで。
- 検証結果：確認対象と結果。未確認・実行不能の範囲があれば併記。
- 残る懸念：判断が必要な点、制約、残作業。なければ不要な説明を増やさない。
- リリース契約・保留中リリースノート：既存の必須形式を保持。

### Issue

- 問題・目的：現在の困りごとと達成したい状態。
- 対象範囲：今回扱うこと。必要な場合だけ対象外も書く。
- 完了条件：確認可能な条件。
- 補足：関連Issue・PR、証拠、設計上の背景。

実装方法を先に固定せず、問題と完了条件を中心にする。
任意改善や高コストの追加テストを根拠なく必須条件にしない。

### ROADMAP

- 冒頭：現在地、残作業、次の行動を数行で。
- 工程表：工程／状態／残る完了条件／根拠。
- 方針・依存関係：全体に関わる前提をまとめる。
- 履歴・詳細証跡：過去の経緯、完了実績、CIなど。

必要な実績を失わずに本文から履歴へ整理する。
進捗同期では既存の更新条件・通知条件を守り、意味のある変更がない場合の書き換えや定型通知を増やさない。

### コメント・作業報告・最終回答

結論や回答を先に、次に必要な理由・根拠、残件や依頼を書く。
通常は短い段落や箇条書きで足りる。
実施したこと、まだ行っていないこと、ユーザーの判断待ちを曖昧にしない。

## 編集例

以下は書き方を示す架空の例であり、実際の進捗記録ではない。

### 整理前

PRのcommitを更新しCIが成功したが試験公開では認証を更新し、保存確認は終わったものの同期は未受入で、実装完了と本番受入は区別し、以前の候補では失敗していたので正式リリースとは扱わず、次は別端末で確認する。

### 整理後

試験公開まで完了しました。残る受入項目は、別端末で保存内容を復元できることです。

- 完了：CI、試験公開、保存確認。
- 次の確認：別端末でProjectと計算結果を開く。
- 公開状態：試験公開。正式リリースは未実施。

認証更新や旧候補の失敗経緯は履歴に、CI結果は直接の根拠リンクに分けます。

## 提出前チェック

- [ ] 冒頭だけで結論・現在地と、必要なら読者の判断／行動が分かる。
- [ ] 本文が時系列の作業日誌になっておらず、1つのまとまりで1つの問いに答えている。
- [ ] 実装・マージ・公開・受入と、検証済み／未確認を正確に区別した。
- [ ] 重複する注意書きを整理し、重大な制約・リスクは残した。
- [ ] 根拠リンク・完了実績・ユーザー編集を保持し、番号には内容名を添えた。
- [ ] 用途と長さに合う構成で、不要な節・定型の受信確認・通知を増やしていない。

このチェックは作成者が行い、確認済み項目を毎回本文へ貼り付ける必要はない。
指示とテンプレートだけで読みやすさを完全保証できるわけではない。
形式チェックで確認できることと、内容のレビューが必要なことを区別する。
