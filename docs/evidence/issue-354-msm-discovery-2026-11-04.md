# MSM Run 不一致の調査と診断

[#354 MSM更新でPreflightと生成時のRun検出が不一致になる障害](https://github.com/Yuto-24/AutoNavLog/issues/354)の原因は未確定。
生成時の検出Runと上流一覧が保存されていないため、上流の一時的不整合とは断定できない。
今回は診断と固定データによる再現を追加し、不一致時の即時停止を維持する。
自動再試行、Workflow再実行、本番公開は行わない。

## 確認した事実

対象は[Actions run 41786004139 の初回試行](https://github.com/Yuto-24/AutoNavLog/actions/runs/41786004139/attempts/1)。
実行ソースは `45e4cb5c73d11445c0f84adf1979415cb90a56f5`。

- [Preflight job 126428176685](https://github.com/Yuto-24/AutoNavLog/actions/runs/41786004139/job/126428176685)は2026年11月4日15:31:45 JSTに成功。
  公開済みRunは `20261103210000`、検出Runは `20261104000000`、要求は25時間。
- [生成 job 126428556146](https://github.com/Yuto-24/AutoNavLog/actions/runs/41786004139/job/126428556146)は15:33:12 JSTに不一致で停止。
  引数は `--hours 25 --full-run --expected-run 20261104000000`。
  生成前の検査で停止しており、この試行による新データの公開はない。
- 両jobのインストールログは `jma-gpv-weather 0.6.0`。
  両段階は同じUTC時間内で、既定の要求開始時刻は06:00 UTCとなる。
  時境界を跨いだ要求範囲の変化は、この初回試行の説明にはならない。
- 調査時の最新試行はattempt 3で、外部起動ゲートが停止していた。
  最新試行のみを返すAPIの結果を初回の障害と混同しない。初回jobはattempt指定で取得した。
  後続試行の停止は、初回のRun不一致の原因を示す証拠ではない。

## 再現できる条件と残る不確実性

同梱の0.6.0ライブラリは、渡された一覧から必要な補間時刻をすべて満たすRunを選ぶ。
一覧を明示して呼ぶ経路ではディスクの一覧キャッシュを使わない。
Preflightと生成の一覧取得は独立しており、同じ要求でも入力が変化すれば結果が変わる。

固定時計・固定一覧と実ライブラリによるテストで、次を区別する。

| 条件 | 生成前の結果 | 処理 |
| --- | --- | --- |
| 同じ完全なRunが最新 | 期待Runと一致 | 既存の生成・検証へ進む |
| 新しい完全なRunが出現 | 期待Runより新しい | 生成前に停止 |
| 期待Runの必要ファイルが一覧から欠落 | 古い完全なRun、または検出不能 | 生成前に停止 |
| 時境界を跨いで必要な予報範囲が延びる | 同じ一覧でも完全性の判定が変化 | 不一致なら生成前に停止 |

これらは再現可能な条件であり、実障害でどの条件が発生したかの確定ではない。
過去の生成時Run・一覧がないため、新Runの出現か一覧の後退かも復元できない。

## 診断の読み方と互換性

`run_discovery` JSONを標準エラーへ出力する。`stage`は`preflight`または`generation`。
`checked_at`、`expected_run`、`discovered_run`、要求開始・終了と時間数を比較する。
Preflightにはまだ承認済みRunがないため`expected_run`はnull。
検出失敗は`status=FAILED`、検出成功は`DISCOVERED`であり、後者は公開許可を意味しない。
Run不一致は従来のValueErrorで停止し、メッセージにも両Runを付加する。

一覧ごとにURLのSHA-256、取得済みテキストのbyte数・SHA-256を記録し、合計件数・byte数も出す。
取得はASCII decodeなのでテキストのUTF-8 byte列は取得内容と一致する。
URL・レスポンス本文・認証情報は出さず、診断用の追加通信もしない。
一覧取得が途中で失敗すると呼出元へ一覧が返らないため、診断の件数は0となる。
これは上流の空一覧を確認した意味ではなく、`FAILED`として扱う。

`refresh_feed`は成功・失敗とも子プロセスの標準エラーを転送する。
既存の標準出力JSON、CLI引数、GitHub outputs、Run一致・完全性・鮮度・公開前検査は維持する。
外部起動予算やno-rerun制約も変更しない。
自動回復の要否は、新しい診断で実際の変化を確認した後の判断とする。
