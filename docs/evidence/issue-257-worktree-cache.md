# Issue #257: worktree MSM cache validation and reclamation

Measured on `matsu2-Win11Pro` (WSL Ubuntu), 2026-10-13 JST. This is one observed host, not a fleet-wide measurement.

## Cause and change

Each generated worktree had its own persistent volume, a real MSM provider, a 48-hour prewarm at startup and every 15 minutes, and a per-cache 20GiB / seven-day prune. That limit did not bound aggregate worktree storage. Base Compose inherited `unless-stopped`. Cache contents strongly explain growth; byte-for-byte duplication across volumes was not established.

Generated overrides now disable prewarm by default and set restart to `no`. Explicit `AUTONAVLOG_MSM_PREWARM=true` retains the existing prewarmer and MSM provider; on-demand preparation is unchanged. CLI and environment-based ASGI factory both strictly parse the flag. Normal runtime defaults remain enabled. No shared cache, production deployment, or primary runtime volume changes.

Cleanup remains a whole-environment disposal action. It now preserves its generated configuration on Docker/Compose failure so an operator can retry. The app-managed Linux environment has setup and cleanup scripts registered; registration does not prove the desktop invoked cleanup for every retained environment. Existing worktrees may still be intentionally retained, and the prior script lost retry configuration when Docker was unavailable.

`Optimize-VHD` requires the Hyper-V PowerShell module and an unattached or read-only-attached disk. Compaction can complete without reducing size; measure the result. Do not zero-fill free space on this capacity-constrained host. See [Microsoft Optimize-VHD documentation](https://learn.microsoft.com/en-us/powershell/module/hyper-v/optimize-vhd) and [WSL disk-space guidance](https://learn.microsoft.com/en-us/windows/wsl/disk-space).
